# Evidence contract standards mapping

**Status:** Optional F006 mapping guidance. OpenARDP does not claim W3C conformance, and
the wire contracts require no JSON-LD context or network vocabulary resolution.

## Mapping posture

The F006 roots are small implementation contracts, not a replacement vocabulary. W3C
PROV and Web Annotation concepts are reused when their semantics align. Provider-profile
details, fixed-point geometry, trust policy, contract versioning, and content-addressed
integrity remain explicit OpenARDP concerns.

| OpenARDP concept | Reusable standards concept | Mapping status |
|---|---|---|
| Original source version | PROV Entity | Reusable; the SHA-256 identifies exact source bytes |
| Native representation | PROV Entity generated by an Activity | Reusable with an explicit parser/generator activity |
| Provider recipe | PROV Activity plus SoftwareAgent association | Profile-specific; configuration identity remains explicit |
| Evidence projection | PROV Entity derived from source/native entities | Reusable; thin-surface restrictions are OpenARDP policy |
| Evidence reference | Web Annotation Specific Resource/Target | Reusable as an optional serialization profile |
| Text span | Text Position Selector | Reusable only for the declared Unicode code-point view |
| Page region | Fragment/selector profile | Profile-specific; normalized PPM and page numbering require profile terms |
| Table cell | Selector scoped to an opaque table target | Deliberately no universal selector claim |
| Provider pointer | State/refined target owned by a provider profile | Opaque; no cross-provider equivalence claim |
| Trust classification | No direct PROV/Web Annotation equivalent | Deliberately unmapped security policy |
| SHA-256/JCS identity | Integrity and canonical identity rule | OpenARDP rule, not a PROV assertion |

## W3C PROV guidance

- Treat original bytes, retained native artifacts, retrieval artifacts, references, and
  projections as entities only when the chosen profile preserves their distinct
  identities.
- Represent parser/projection execution as activities associated with identified
  software agents. Do not collapse generator version and configuration hash into an
  unverifiable free-text label.
- `wasDerivedFrom` may relate a projection to the exact source and native entities, but
  it does not replace OpenARDP's required source/native identifiers.
- Creation time maps naturally to generation time. It is lifecycle evidence and remains
  excluded from content identity.
- Trust zones and instruction authority are security controls, not provenance claims.

## Web Annotation guidance

- An `EvidenceReference` can be serialized as a target-specific resource with a selector.
- A text anchor resembles a text-position selector, but its coordinate system is only
  meaningful for the named provider-profile text view.
- A page rectangle requires an explicit optional profile describing one-based pages,
  top-left origin, right/down axes, and integer parts-per-million.
- A table-cell target and opaque provider pointer require provider-profile semantics.
  Consumers must retain the native artifact and must not infer equivalence from matching
  pointer strings.
- Annotation bodies, motivations, agents, and remote contexts are not required by F006.

## Non-mappings and safety

- Schema `$id` and namespace URIs are identifiers, not instructions to fetch.
- Provider pointers are never treated as paths, URLs, object deserialization directives,
  or capabilities.
- JSON-LD expansion, remote context loading, RDF canonicalization, and graph reasoning
  are outside F006.
- An optional mapping must preserve exact OpenARDP contract identities or declare a
  lossy/export-only relationship.
- Feature 016 tested both directions with an isolated standard-library consumer and a
  non-Docling TXT/CSV producer. The complete F006 fixture corpus and all six identity
  vectors passed independently; the reference implementation accepted the alternate
  text, page-region, table-cell and opaque-pointer record sets.

## F016 bounded decision

The result supports provider neutrality only for the measured thin contract surface:
identity, source/native binding, navigation anchors, retrieval handles, trust and lifecycle
metadata. No Docling-named field or value leaked into alternate records.

Observed friction remains explicit:

- JSON Schema cannot express all identity, scope, trust and record-set invariants, so an
  independent consumer must implement both structural and semantic validation layers.
- Purpose-specific RFC 8785 identity allowlists must be reproduced exactly. The current
  golden evidence covers the contract's integer/string/no-float identity domain, not a
  general-purpose numeric JCS implementation.
- Page geometry is provider-declared, while table and provider pointers remain opaque and
  profile-scoped. Matching shapes do not prove equivalent parser semantics.

No contract change is required by the spike. Contract `0.1.0` remains experimental because
an internal independent process is not external adoption and no breaking-contract migration
practice has yet been demonstrated. The canonical machine decision is
`conformance/alternate-parser/v0.1.0/expected/decision.json`.
